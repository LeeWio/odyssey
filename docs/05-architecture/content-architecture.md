# 内容架构

## 定位

内容架构定义 Odyssey 如何组织、编辑、发布、检索和展示内容。项目的内容不只是博客文章，还包括评论、时间线、音乐记录、股票记录、友链、项目、作品集和未来可能扩展的个人知识模块。

## 内容类型

当前系统可识别的主要内容类型包括：

- 文章：长文、技术记录、审美分析、日志。
- 评论：文章评论、留言板树形回复、后台审核对象。
- 分类与标签：文章组织与检索维度。
- 富文本草稿：编辑器中的 Tiptap JSON 内容。
- 音乐数据：音乐模块和 Vae song battle 相关数据。
- 友链：外部站点与社交连接。
- Moment：短内容或动态记录。
- Project / Portfolio：项目与作品展示。
- Dashboard 数据：分析、订单、用户、权限等管理面板数据。

## 内容生命周期

```text
Draft
  -> Normalize
  -> Validate Metadata
  -> Publish / Update
  -> Query
  -> Render
  -> Interact
  -> Moderate / Archive
```

## 文章内容模型

文章以 `Post` 为核心实体，关键字段包括：

- `title`：标题。
- `slug`：路由标识。
- `coverImage`：封面图。
- `summary`：摘要。
- `content`：正文内容，当前发布链路中以 JSON 字符串保存 Tiptap 内容。
- `status`：`DRAFT`、`PUBLISHED`、`ARCHIVED`。
- `category`：分类。
- `tags`：标签集合。
- `series`：系列归属。
- `views`、`likesCount`、`favoritesCount`：互动统计。

组件不得假设后端字段永远非空。API schema 应在边界处对 nullable 字段进行默认值处理。

## 编辑器内容

富文本编辑器使用 Tiptap。编辑态内容以 `JSONContent` 表示，发布前通过工具函数执行：

- 文档结构标准化。
- 标题提取。
- slug 生成。
- 摘要提取。
- 内容序列化。

规则：

- 编辑器内部操作使用 Tiptap JSON。
- 发布到文章接口前进行标准化。
- 不在展示组件中反向推断编辑器状态。
- 草稿 active id 可通过 UI slice 和本地持久化恢复。

## 内容展示

内容展示分为列表展示和详情展示：

- 列表页优先消费 digest 数据，避免加载完整正文。
- 详情页根据 slug 获取完整文章内容。
- 阅读视图负责正文渲染、阅读进度、侧栏和相关交互。
- 首页可展示内容摘要或精选内容，但不应成为文章业务逻辑的来源。

## 评论内容

评论支持树形结构。评论数据应在 API 层归一化为稳定的 children 数组，组件不应处理 `null` children。

评论架构规则：

- 公开接口用于文章评论和留言板。
- 管理接口用于审核、状态变更和删除。
- 评论发布后通过 RTK Query tag 失效刷新对应文章评论树。
- 评论状态由后端负责最终裁决，前端只展示操作入口和结果反馈。

## 分类与标签

分类和标签是内容组织能力，不是纯 UI 筛选器。

规则：

- 分类适合表达内容的主归属。
- 标签适合表达横向主题。
- 分类和标签查询应走独立 feature API。
- 发布文章时只传递分类 id 和标签 id 列表。
- 页面展示应消费经过 API 层处理后的完整对象。

## 内容检索

文章搜索模型包含标题、摘要、正文、作者、分类、标签、发布时间和浏览量等字段。统一搜索结果应转化为可直接渲染的 command item/group，而不是让命令面板理解各业务实体的细节。

## 本地内容数据

`data/` 目录当前可承载轻量演示或局部持久化数据，例如分享列表。该目录不应成为正式业务数据库。

使用规则：

- 仅用于局部模块、演示数据或降级数据。
- 写入逻辑必须处理文件不可写场景。
- 生产业务数据应迁移到后端服务。

## 内容扩展规则

新增内容类型时必须回答：

- 这是核心内容、支持内容还是实验内容？
- 是否需要后台管理？
- 是否需要检索？
- 是否需要分类、标签或权限？
- 是否需要编辑器支持？
- 是否需要评论或互动？
- 是否有生命周期状态？

如果答案涉及多个模块，应先补充模块文档或 ADR，再实现。
