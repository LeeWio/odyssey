# 错误架构

## 目标

错误架构用于让系统在接口失败、鉴权失效、外部服务不可用、渲染异常和用户输入错误时保持可理解、可恢复和可观测。错误处理不是简单 toast，而是从边界到交互的完整策略。

## 错误分类

- 用户输入错误：表单缺失、格式非法、内容不完整。
- 网络错误：断网、超时、请求被阻断。
- 后端业务错误：权限不足、资源不存在、状态冲突。
- 鉴权错误：token 过期、401 未授权。
- 响应格式错误：后端返回结构不符合前端 schema。
- 外部服务错误：第三方 API 不可用、资源缺失、重定向失败。
- 渲染错误：React 组件异常、客户端运行时错误。
- 持久化错误：LocalStorage、Cookie 或文件写入失败。

## 错误处理层级

```text
Input Validation
  -> API Boundary
  -> Data Transformation
  -> Cache / State Recovery
  -> UI Error State
  -> Global Error Boundary
  -> Observability
```

## API 错误

`baseApi` 提供统一错误转换能力。

当前标准处理：

- 后端返回 `data.message` 时优先使用后端消息。
- 403：权限不足。
- 413：上传文件过大。
- 429：请求过于频繁。
- `FETCH_ERROR`：网络错误。
- `PARSING_ERROR`：服务端响应不可解析。
- `TIMEOUT_ERROR`：请求超时。
- `CUSTOM_ERROR`：自定义请求错误。

组件应优先使用 API 层转换后的错误，不应重复实现通用状态码文案。

## 鉴权错误

401 是全局鉴权边界错误。

处理策略：

- 在 `baseApi` 中拦截 401。
- dispatch `auth/removeCredentials`。
- 清除本地鉴权持久化。
- 避免继续使用过期 token。
- 由 UI 根据认证状态展示登录入口或受限状态。

注意：权限最终由后端裁决。前端不应把角色判断当作安全边界。

## 用户输入错误

表单输入错误应在发起 mutation 前尽早发现。

规则：

- 必填字段在组件层校验。
- 领域格式在提交前校验。
- 后端返回的业务错误必须展示给用户。
- 不要只在 console 中记录用户可修复错误。

例如富文本发布必须校验 title 和 slug，不应提交空标题到后端再依赖后端失败。

## 响应格式错误

Zod schema 是响应边界的防线。

策略：

- 对可空字段设置合理默认值。
- 对递归结构使用明确 schema。
- 对分页结构统一校验。
- schema 失败时应视为后端契约错误，而不是组件问题。

后续如果引入日志平台，应将 schema 失败作为高优先级接口契约异常记录。

## Route Handler 错误

Route handler 必须返回明确 HTTP 状态码和简洁错误体。

规则：

- 参数缺失返回 400。
- 外部服务失败透传或映射合理状态码。
- 资源不可用返回 404。
- 未预期异常返回 500。
- 不向客户端泄露内部堆栈。
- 服务端记录足够诊断信息。

音乐流解析接口应特别注意第三方服务不稳定和 mixed content 问题。

## UI 错误状态

组件必须区分：

- loading
- empty
- error
- unauthorized
- success

禁止把所有失败都显示为“暂无数据”。空态表示请求成功但没有数据，错误态表示请求失败。

## 全局渲染错误

`app/error.tsx` 是 App Router 的客户端错误边界。它应负责：

- 捕获路由段内渲染异常。
- 提供用户可理解的失败信息。
- 提供重试能力。
- 避免整个应用白屏。

页面级组件仍应处理自己的数据错误，不应把可预期请求失败抛给全局错误边界。

## Toast 使用规则

适合使用 toast：

- 创建成功。
- 更新成功。
- 删除成功。
- 用户操作失败且需要即时反馈。
- 权限或频率限制提示。

不适合只使用 toast：

- 页面主要数据加载失败。
- 表格、列表、详情无法展示。
- 长时间后台任务状态。
- 需要用户修正多个字段的表单错误。

## 持久化错误

LocalStorage、Cookie、文件系统写入都可能失败。

策略：

- 客户端持久化必须包裹 try/catch。
- 持久化失败不应阻塞核心 UI。
- 文件写入失败时 route handler 可以降级为内存模式。
- 不把持久化成功作为业务成功的唯一依据。

## 新功能错误检查清单

- 输入错误在哪里校验？
- API 错误如何转换？
- 401 是否走全局清理？
- loading、empty、error 是否分开？
- mutation 成功和失败是否有明确反馈？
- 外部服务失败是否可恢复？
- schema 失败是否能定位接口契约？
- 用户是否知道下一步该怎么做？
