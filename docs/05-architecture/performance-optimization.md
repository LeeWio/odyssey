# 性能优化专题

## 定位

本文记录 Odyssey 当前 Web 性能问题的判断、优化原则、实施顺序和验收标准。目标是让公开内容页面在首次访问、硬刷新和路由切换时都保持稳定的首屏，不让客户端缓存、动画或低优先级请求决定主要内容何时出现。

本文覆盖公开内容页面及其公共渲染基础设施，优先处理 `/single`、`/single/[slug]` 和 `/moments`。鉴权页面、编辑器和复杂 dashboard 仅在影响公共 bundle 或全局运行时成本时纳入评估。

## 当前基线

当前性能问题主要来自渲染边界、缓存生命周期和首屏时序，而不是单个接口响应速度：

- `app/layout.tsx` 读取请求 `headers()`，使根布局保持动态。公开页面无法仅依赖静态页面缓存获得稳定的服务端响应。
- 页面硬刷新会重新创建 Redux store，RTK Query 的内存缓存随之清空。后端缓存命中不会自动填充浏览器内的 RTK Query cache。
- `/single` 和 `/moments` 的首屏内容曾由 Client Component 在 hydration 后发起请求，因此空缓存时会先进入 loading 或 skeleton 状态。
- 列表页不应为了首屏而序列化完整文章正文；公开列表应优先使用轻量 digest 数据。
- 在内容已经绘制后再使用 GSAP `from` 将元素设为透明，会造成可见闪烁和首屏不稳定。
- shader、WebGL、动态媒体和附加模块会与关键内容争夺主线程和网络资源。它们不能阻塞首屏文本、列表骨架结构或主要交互。
- moments 页面还存在 cadence、发现内容等次要请求，它们的失败或延迟不应让主要 feed 退回 skeleton。

## 性能目标

优化以真实用户感知和可回归测量为准。每次阶段性改动都应记录移动端和桌面端的结果，基线变化需要附带原因。

| 指标     | 目标                                          | 适用页面                        |
| -------- | --------------------------------------------- | ------------------------------- |
| LCP      | 移动端和桌面端达到良好阈值，且不被动画延迟    | `/single`、`/moments`、文章详情 |
| FCP      | 首屏结构和关键文本尽快可见                    | 所有公开页面                    |
| TTFB     | 服务端缓存命中时保持稳定，异常接口不拖住页面  | 公开内容页面                    |
| CLS      | 首屏加载后主要内容位置不跳动                  | 所有公开页面                    |
| INP      | 列表点击、分页和返回操作保持及时              | 列表与详情                      |
| 请求数   | 首屏不重复请求同一页公共数据                  | `/single`、`/moments`           |
| 首屏状态 | 有可用数据时不显示 skeleton；刷新时不闪空状态 | 公开列表                        |
| 动画成本 | 动画优先使用 transform/opacity，不阻塞内容    | 路由切换和列表入场              |

初始验收重点不是追求单一分数，而是确认：服务端已有数据时首屏直接显示内容；客户端 hydration 不重复请求第一页；后台刷新不会清空已有内容；低优先级模块不会改变首屏稳定性。

## 渲染策略

公开且可缓存的初始数据采用“Server Component 首屏 + Client Component 交互”的边界：

1. 页面 Server Component 获取首屏所需的轻量公开数据。
2. 服务端请求必须使用现有 Zod schema 校验响应，并设置明确的超时和错误降级。
3. Client Component 接收 `initialData`，将其作为首屏可用数据，并跳过同一页的重复 RTK Query 请求。
4. 分页、筛选、点赞、评论、加载更多等交互继续由客户端状态和 RTK Query 管理。
5. 详情页按需获取正文，不把完整正文带入列表页的服务端 payload。
6. 鉴权、个性化和依赖浏览器状态的数据继续保持客户端获取，避免把用户状态错误地放入公共缓存。

Client Component 只包住需要 state、effect、浏览器 API、事件和动画的部分。页面壳、首屏数据组装和静态结构尽量保持服务端渲染。

## 缓存策略

缓存分为服务端公共缓存和客户端交互缓存，两者职责不同：

- Next.js 服务端 fetch 对公开列表使用 `revalidate`，并通过稳定的 tag 支持失效。
- 公共数据的缓存时间按内容更新频率设置，默认从 60 秒开始，后续根据实际发布频率调整。
- 服务端请求失败时返回可处理的空结果或错误状态，不在构建阶段强依赖运行中的业务 API。
- RTK Query 继续负责 hydration 后的交互缓存、分页缓存、mutation 失效和请求状态。
- `initialData` 只用于填充首屏，不复制成另一份长期 Redux 状态；客户端应保持单一的数据所有权。
- mutation 成功后必须通过既有 tag 或明确的重新验证策略使服务端和客户端缓存最终一致。
- 不把“后端接口有缓存”当作“浏览器刷新后 Redux 仍有缓存”。硬刷新后的首屏必须由服务端数据、持久化策略或明确的 loading 设计负责。

## Loading、错误与刷新策略

页面状态按“是否有可用数据”区分，而不是只看请求是否正在进行：

- 没有任何数据且首次请求进行中时，显示与最终布局一致的 skeleton。
- 已有首屏数据时，后台刷新使用 `isFetching` 等非阻塞状态，不替换内容，不退回 skeleton。
- 加载更多只影响列表尾部，不覆盖已有条目。
- 次要请求失败时保留主要内容，并在对应模块局部降级。
- 服务端首屏获取失败时，客户端仍可尝试 RTK Query 请求；客户端失败时显示可恢复的错误和重试入口。
- 空数据、错误和加载状态必须保持稳定尺寸，避免由状态切换造成 CLS。

## 动画与媒体策略

动画服务于内容关系和交互反馈，不负责让关键内容“变得可见”：

- 首屏关键文字、标题、列表和主要操作在没有动画完成时也必须可见。
- 不对已经绘制的内容使用会先设置 `opacity: 0` 或 `autoAlpha: 0` 的入场动画。
- 路由切换动画优先使用 View Transition API 或 `motion/react`；GSAP 仅在时间线、跨元素编排或已有实现确有必要时使用，并记录例外原因。
- 动画只改变 transform 和 opacity，避免在每一帧读取布局或触发大范围重排。
- 尊重 `prefers-reduced-motion`，减少位移、缩短过渡，并保留即时导航能力。
- shader/WebGL 先提供静态封面或普通图片，再异步初始化增强效果；初始化失败不能影响内容阅读。
- 首屏只保留必要媒体，非关键图片和动态模块延迟到内容稳定后加载。

## 实施阶段

### 阶段一：首屏数据前置

- 为公开列表页建立服务端初始数据 loader。
- 使用轻量 digest schema，避免把不需要的正文和关联数据序列化到页面。
- 将首屏数据传入客户端组件，跳过第一页重复请求。
- 覆盖 `/single` 和 `/moments`，再扩展到其它公开列表。

### 阶段二：消除首屏闪烁与布局跳动

- 删除会在 paint 后隐藏内容的入场动画。
- 统一首屏 loading、empty、error 的稳定尺寸。
- 检查 hydration 前后主题、语言和布局是否一致。
- 使用移动端和桌面端截图验证硬刷新、返回和路由切换。

### 阶段三：降低次要请求优先级

- 梳理 cadence、发现内容、facets、推荐和统计请求。
- 让主要内容先完成，再延迟非关键模块。
- 后台刷新只更新对应模块，不清空主列表。
- 对重复请求、无效请求和仅为装饰服务的请求进行删除或合并。

### 阶段四：媒体、shader 与 bundle 优化

- 统计 shader/WebGL 初始化耗时和失败率。
- 为视觉增强提供静态 fallback，限制同时运行的实例数量。
- 检查重型依赖是否被公共 layout 或所有路由加载。
- 对文章详情、编辑器和实验模块保持路由级或组件级拆包。
- 图片使用合适尺寸、格式和加载优先级，避免大图抢占首屏资源。

### 阶段五：建立回归检查

- 固定移动端和桌面端的 Lighthouse/Web Vitals 测量入口。
- 使用 Playwright 验证硬刷新不先显示错误 skeleton、首屏不闪烁、分页仍可用。
- 记录首屏请求数量，并断言第一页不会在服务端数据后重复请求。
- 验证 reduced motion、慢网络、接口失败和空数据状态。
- 每次影响公共渲染边界的改动都更新本文的基线和风险记录。

## 验证方法

每个优化阶段至少完成以下检查：

- `npm run lint` 或项目对应的 lint 命令。
- `tsc --noEmit` 或项目对应的类型检查。
- `git diff --check`。
- 生产构建；若构建依赖外部 API，必须记录依赖条件和降级行为。
- Playwright 硬刷新、站内跳转、返回、加载更多和 reduced motion 场景。
- 桌面端和移动端首屏截图，确认无内容闪烁、遮挡、布局跳动和空白主区域。
- 网络面板确认公共第一页没有重复请求，次要请求不会阻塞主要内容。

## 风险与边界

- 服务端数据和客户端数据的 schema 或排序不一致，可能导致 hydration 差异或列表重复。
- 公共缓存会带来短时间陈旧数据，必须根据内容更新路径设置合理的 `revalidate` 和失效 tag。
- 构建环境可能无法访问业务 API，loader 必须有超时和构建阶段降级策略。
- 个性化、鉴权和依赖 Cookie 的数据不能误用公共缓存。
- 同时保留服务端初始数据和客户端查询时，必须明确第一页的去重规则，避免请求和状态双写。
- shader 和动画优化可能改变视觉节奏，必须以 `docs/04-design/animation.md` 与可访问性要求为约束。

## 完成定义

当以下条件同时满足时，公开内容页面的性能专题可视为完成第一轮：

- `/single` 和 `/moments` 硬刷新时直接呈现服务端初始内容，不因 RTK Query 空缓存先进入整页 skeleton。
- 首屏 hydration 不重复请求已经由服务端提供的第一页。
- 后台刷新、分页和次要模块加载不会清空已有主要内容。
- 关键内容不依赖入场动画，不出现可见闪烁或明显布局跳动。
- 失败、空数据、慢网络和 reduced motion 场景有稳定且可恢复的行为。
- lint、类型检查、生产构建和关键 Playwright 验证均有记录。

## 当前实施记录

第一轮全局优化已完成以下改动：

- `/single` 和 `/moments` 的公开首屏数据改为服务端提供，客户端跳过第一页重复请求。
- `/moments` 的 cadence 数据纳入服务端初始 payload，服务端失败时保留客户端兜底。
- 首页 shader 和 Lenis/GSAP 平滑滚动增强改为按需加载，降低公共首屏 chunk 的重型依赖。
- 媒体播放器改为首次播放时才创建 `Audio` 实例，普通页面加载不再初始化音频对象。
- RTK Query 未使用数据的保留时间统一提高到 300 秒，减少站内返回和短时间切换时的重复请求。
- 修正导航组件在 render 阶段写入 state 的问题，并移除导航纯配置文件多余的 Client Component 边界。
- 首页平滑滚动现在真正遵守 `prefers-reduced-motion`。
- shader 卡片调度器改为按实例生命周期注册和移除全局 scroll/resize 监听，避免空页面持续调度。
- 文章阅读进度条按百分比变化更新 React 状态，并复用 glow tween；阅读操作栏只在阈值变化时更新状态。
- Moments 登录用户的点赞状态改为列表级批量查询，避免每张卡片产生独立请求。
